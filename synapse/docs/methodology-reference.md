## 4. 五层自检金字塔 — Synapse 定制版

GlassCortex 的五层是为代码产物设计的。Synapse 将同一套分层逻辑映射到**设计产物**（文档、模型、协议）和未来的**代码产物**。

### 通用框架

| 层 | 检查什么 | 核心问题 |
|---|---------|---------|
| L1 结构 | 产物本身是否完整、格式是否正确 | "写得对不对？" |
| L2 引用 | 产物中引用的东西，真的存在吗？ | "指的东西在吗？" |
| L3 契约 | 多个产物之间的约定，是否一致？ | "说的和做的一致吗？" |
| L4 场景 | 真实使用场景下，能走通吗？ | "用起来会炸吗？" |
| L5 人因 | 新人/新会话能从文档快速定位吗？ | "换个脑子还能懂吗？" |

### 设计阶段（当前：无代码）

| 层 | Synapse 设计阶段检测手段 |
|---|------------------------|
| L1 结构 | 文档结构完整、格式统一、术语一致 |
| L2 引用 | 文档间交叉引用可解析、外部链接有效、文件路径真实存在 |
| L3 契约 | 数据模型 vs 协议 vs PRD 三方对齐——一个决策改了，另外两个文档同步更新 |
| L4 场景 | 取一个具体用户故事，在数据模型和协议上逐步推演——每一步状态变更是否可记录、信息是否充分 |
| L5 人因 | 找一条非作者的用户旅程（README → PRD → 数据模型 → 第一个场景），检查每步文档是否可独立理解 |

### 代码阶段（未来）

| 层 | Synapse 代码阶段检测手段 |
|---|------------------------|
| L1 结构 | lint + typecheck + build 全绿 |
| L2 引用 | import/API 路径/配置 key 交叉验证 |
| L3 契约 | API schema snapshot + 消费者编译检查 |
| L4 场景 | 端到端测试 + 浏览器运行时验证 |
| L5 人因 | UI 状态遍历 + 错误信息可读性 + 接入文档准确性 |

### 五层分级矩阵 — 按变更类型选择性执行

> 从 GlassCortex 审计移植（2026-07-06）。并非每批都需要全五层——按变更类型自动确定必做/可跳过的层级，减少无意义的检查步骤，防止五层纪律被稀释。

**设计阶段（当前）**：

| 变更类型 | 典型 Batch | L1 结构 | L2 引用 | L3 契约 | L4 场景 | L5 人因 |
|:---------|:----------|:------:|:------:|:------:|:--------:|:------:|
| 📝 内容/文档 | 文档更新、需求日志、日报 | ✅ 必做 | ⬚ 跳过 | ⬚ 跳过 | ⬚ 跳过 | ✅ 文档新鲜度 |
| 🏗️ 设计/建模 | 数据模型、协议、PRD 变更 | ✅ 必做 | ✅ 交叉引用 | ✅ 三方对齐 | ✅ 场景推演 | ✅ 叙事一致性 |
| 🔀 混合 | 跨层设计变更（PRD+模型+协议同批） | ✅ 必做 | ✅ 必做 | ✅ 必做 | ✅ 必做 | ✅ 全三项 |

**代码阶段（未来）**：

| 变更类型 | 典型 Batch | L1 语法 | L2 引用 | L3 契约 | L4 运行时 | L5 人因 |
|:---------|:----------|:------:|:------:|:------:|:--------:|:------:|
| 📝 内容/文档 | 文档更新、需求日志、日报 | ✅ 必做 | ⬚ 跳过 | ⬚ 跳过 | ⬚ 跳过 | ✅ 文档新鲜度 |
| 🧩 UI 组件 | 前端组件、CSS、交互态 | ✅ 必做 | ✅ CSS 专项 | ⬚ 跳过 | ✅ 浏览器 | ✅ 状态遍历 |
| ⚙️ 后端/引擎 | API、存储、协调引擎 | ✅ 必做 | ✅ 引用完整性 | ✅ 契约兼容 | ⬚ 跳过 | ✅ 叙事一致性 |
| 🔀 混合 | 跨栈变更、共享模块重构 | ✅ 必做 | ✅ 必做 | ✅ 必做 | ✅ 必做 | ✅ 全三项 |

**分级规则**：
- **L1 永远是必做项**——不管改什么类型都不豁免。`make check`（或设计阶段的文档结构检查）全绿是所有 Batch 的基线。
- **L2（引用）对纯内容跳过**——文档不涉及代码/设计引用。UI 组件只做 CSS 专项（硬编码值、孤儿类、设计令牌一致性），不跑全量引用检查。
- **L3（契约）只有接口/协议变更时才做**——纯内容或纯 UI 无需契约检查。
- **L4（运行时/场景）只有涉及交互行为或跨系统推演时才做**——纯后端逻辑变更不需要打开浏览器（代码阶段），纯文档变更不需要场景推演（设计阶段）。
- **L5（人因）所有人都必做但子项不同**——纯内容只做文档新鲜度，UI 组件追加状态遍历，后端/设计追加叙事一致性。

**为什么分级**：全五层每批跑 → L2 引用检查对纯文档 Batch 是纯粹浪费 → 五层纪律被稀释（"又是全五层，扫一眼就过"）。分级让每次自检有意义——每层只在它真正能发现问题的场景下执行，纪律不贬值。

### 频率与触发

- **L1-L4**：每批按[五层分级矩阵](#五层分级矩阵--按变更类型选择性执行)选择性执行——不是每批跑全套，而是按变更类型匹配必做层级
- **L5**：每 2 批拉通一次。**第 2 批文档闭环前必须执行，不等下批 Pre-flight 拦截**。L5 复位与功能 Batch **合并在同一 commit**（不再拆分独立 L5 doc commit — P100-B70 流程瓶颈修复）

### L5 子项选择器 — 按变更类型自动确定检查清单

L5 包含三个子项，但并非每次拉通都需要执行全部三项。按累积 Batch 的变更类型自动选择：

**设计阶段（当前）**：

| 子项 | 检查内容 | 📝 内容/文档 | 🏗️ 设计/建模 | 🔀 混合 |
|:----|:---------|:-----------:|:----------:|:------:|
| 🎭 场景/状态遍历 | 取关键用户故事，逐步推演全部状态节点——初始化/更新/异常/销毁各路径是否覆盖 | ⬚ 可跳过 | ⬚ 可跳过 | ✅ 必做 |
| 📚 叙事跨批一致性 | 累积 Batch 间的文档叙事链是否自然承接、术语是否统一、决策是否前后矛盾 | ✅ 必做 | ✅ 必做 | ✅ 必做 |
| 📄 文档新鲜度 | roadmap/requirements-log/pitfalls 等日期戳是否与当前状态同步 | ✅ 必做 | ✅ 必做 | ✅ 必做 |

**代码阶段（未来）**：

| 子项 | 检查内容 | 📝 内容/文档 | 🧩 UI 组件 | ⚙️ 后端/引擎 | 🔀 混合 |
|:----|:---------|:-----------:|:--------:|:----------:|:------:|
| 🎭 状态组合遍历 | 全部 UI 状态组合肉眼过一遍；每个用户操作是否有反馈 | ⬚ 可跳过 | ✅ 必做 | ⬚ 可选 | ✅ 必做 |
| 📚 叙事跨批一致性 | 内容/文档的叙事链是否自然承接前文、跨批有无矛盾 | ✅ 必做 | ⬚ 可跳过 | ⬚ 可选 | ✅ 必做 |
| 📄 文档新鲜度 | roadmap/requirements-log/pitfalls 等是否与当前状态同步 | ✅ 必做 | ✅ 必做 | ✅ 必做 | ✅ 必做 |

**选择器规则**：
- **📄 文档新鲜度是所有人的必做项**——不管改什么类型都不豁免。这是 L5 的最低基线。
- 🎭 状态遍历对纯内容可跳过——文档变更没有 UI 状态可遍历。设计阶段对纯文档也可跳过。
- 📚 叙事一致性对纯 UI 可跳过——组件样式变更不改变文档叙事链。
- 变更类型由执行者自判（基于 git diff 的文件类型分布），在 L5 报告首行标注。

**为什么需要选择器**：如果 L5 每次强制做全部三项：(a) 对纯内容修改，状态组合遍历毫无意义且白做→削弱 L5 纪律的长期可信度；(b) 对 UI 改造，跳过遍历等于白做 L5。按类型自动选择检查清单，让 L5 的「必做」每次都有意义——纪律不被稀释。

### L5 结构化报告模板

> 从 GlassCortex 审计移植（2026-07-06）。L5 检查报告使用统一模板写入 requirements-log，确保每次 L5 深度一致、可追溯、可对比。

**模板**：

```markdown
### YYYY-MM-DD — L5 拉通自检 (Phase N Batch X~Y 累积 · K 批) ✅

L5 拉通 [变更类型: content | design | ui | api | mixed]

🎭 场景/状态遍历：[必做/可跳过] — <结论或"纯内容，跳过">
📚 叙事跨批一致性：[必做/可跳过] — <结论或"纯 UI，跳过">
📄 文档新鲜度：[必做] — <结论>

L5 置信度：<0.0-1.0>（<理由：是否全覆盖 / 是否有盲区>）

**结论**：L1-L5 全绿 ✅ — 准予推进 Phase N Batch Z
```

**字段说明**：

| 字段 | 说明 |
|------|------|
| `变更类型` | 从 L5 子项选择器匹配：`content`（纯内容/文档）· `design`（设计建模）· `ui`（UI 组件）· `api`（后端/引擎）· `mixed`（混合） |
| `K 批` | 累积未拉通的 Batch 数 |
| `[必做/可跳过]` | 严格按选择器表判定——不是主观判断，是变更类型决定的 |
| `L5 置信度` | 0-1 之间。1.0 = 所有必做子项全覆盖且无盲区。0.7 = 某项跳过了但有合理理由。≤0.5 = 有未覆盖的盲区，需在下批 L5 补充 |

**使用规则**：
- 若某项跳过，标注理由（如「纯内容修改，无 UI 状态变更」），确保跳过本身可追溯
- L5 报告直接写入 requirements-log，与对应 Batch 条目相邻
- L5 拉通时不再重复 L1-L4 的细节——L1-L4 已在各自 Batch 的 requirements-log 条目中记录。L5 只做跨批层面的叙事一致性和文档新鲜度检查

**为什么模板化**：L5 自由格式 → 深度不一致（有时 3 行带过，有时写满半页）→ 阅读者无法判断「这次 L5 是认真做了还是走形式」。模板强制标注变更类型、各子项结论和置信度——模板不是建议，是让每次 L5 可审计。

- **L1-L4 记录硬约束**：每批在 requirements-log 中列出 L1-L4 breakdown，不能只写"验证通过"

## Shared Module Governance（轻量版）

> 从 GlassCortex 移植核心概念。完整治理留到代码阶段（Synapse 当前消费者 <3）。

### 风险模型

任何被 N 个消费者引用的共享模块，其返修成本不是线性而是乘数效应：

```
Risk = N(消费者数) × Σ(每层未枚举的边界条件数)
```

| 等级 | 条件 | 动作 |
|------|------|------|
| 🔴 Critical | N ≥ 10 且 K ≥ 3 | Plan 必须做完整 Consumer Impact Analysis + Layer Enumeration |
| 🟠 High | N ≥ 5 且 K ≥ 2 | Plan 必须做两项分析 |
| 🟡 Medium | N ≥ 3 | Plan 建议做分析 |

### 品类-层模板（参考框架）

| 品类 | 典型模块 | 抽象层数 | 推荐验证策略 |
|------|---------|:------:|------------|
| 数据模型 | schemas、类型定义 | 5 层 | 消费者兼容测试 |
| 数据存储 | store、index | 5 层 | 迁移测试 |
| 配置模块 | config、环境变量 | 5 层 | 环境矩阵测试 |
| 业务引擎 | planner、coordinator | 5 层 | 消费者契约测试 |
| 渲染引擎 | 格式化、可视化 | 5 层 | 浏览器渲染快照 |

> GlassCortex 的 renderMarkdown 12 次返修是共享模块风险的典型实例：5 consumers × 5 layers × ~2.4 missed conditions/layer ≈ 12 fix rounds。详见 GlassCortex methodology.md §Shared Module Governance。

## 反模式速查

> 新 AI Session 开工前 30 秒自检：扫一遍下表，确认自己不在任何反模式中。

### 流程反模式（开工/收尾阶段）

| 反模式 | 症状 | 纠正 |
|--------|------|------|
| 无 Plan 开写 | 设计到一半发现概念冲突，返工 | 按 [Plan 分级](#plan-分级--按-batch-规模选择-plan-模式) 匹配模式——≥3 文件或接口变更时 EnterPlanMode |
| 一把梭 | 一个 Batch 覆盖 PRD + 数据模型 + 协议 | 拆到 ≤4 任务，每个可独立验证 |
| 小改动豁免幻觉 | 「就改一行」→ 跳过 Plan/门禁/五层自检 | **零例外**：1 行和 100 行走同一套启动流程。Plan 形式可简化（🟢 inline），流程步骤不跳 |
| 分级降级 | 本该 🔴 大型的变更用「不想写完整 Plan」降为 🟡 | 判断标准是客观条件（文件数+接口影响），不是主观感受 |
| 交付后才跑门禁 | `check-docs` 放 Batch 末尾 → L5 已欠债多批才发现 | 开工前第一件事 `./tools/check-docs.sh`，L5 >2 批先拉通再开工 |
| 跳过 hook | `--no-verify` 绕过检查 | 修问题，不绕检查。hook 拦住的东西就是该修的 |
| 模糊 commit | `fix` / `update` / `wip` | `feat(synapse): Phase N Batch M — 做了什么 + 为什么` |
| Plan 堆积 | `docs/plans/` 积累 10+ 历史 Plan | 推送后立即清理。Git history 保留了设计意图 |
| 选项瘫痪（V-006） | Plan 出 A/B/C 选项后逐条问用户选方向，而非推荐+执行 | 推荐最优方案并给出理由，直接执行。用户修正方向比从零决策成本低 |
| 需求粒度假豁免（V-015） | 范围明显超 8 文件红线但用「差不多能做完」跳过拆分 | Plan 阶段逐文件计数，≥9 拆 Batch。§4 粒度控制已有机械门禁，本条是行为层提醒 |

### 质量反模式（验证/自检阶段）

| 反模式 | 症状 | 纠正 |
|--------|------|------|
| L1 即交付 | 文档格式对了就认为「写完了」 | 走完五层分级矩阵匹配的 L2-L5 再报完成 |
| 五层稀释 | 「又是全五层，扫一眼就过」→ L2-L5 走过场 | 按[五层分级矩阵](#五层分级矩阵--按变更类型选择性执行)只跑必做层级——每次自检有意义，纪律不贬值 |
| 警告即门禁 | 发现不一致只口头提「后面再改」→ 4 批后仍未改 | 门禁必须硬阻断（`exit 1`）。能自动判断的违规就必须自动拦截 |
| 凭猜测调参数 | 改设计参数不推演场景 → 改了等于没改 | 字段变更 → grep 全项目 → 场景推演全覆盖 → 确认无断裂 |
| 批量替换不验证（V-016） | `replace_all` / `sed` 多文件替换后不逐文件检查，漏掉边界 case | 替换后 `grep` 旧模式确认零残留，抽样验证 ≥20% 文件完整性 |

### 文档反模式（闭环/记录阶段）

| 反模式 | 症状 | 纠正 |
|--------|------|------|
| 文档过期 | PRD 更新了但数据模型停在旧版本 | L3 契约交叉验证 + 日期新鲜度自动检查 |
| 文档膨胀 | requirements-log 无限增长、CLAUDE.md 只加不删 | 定期归档（保留最近 3 Phase）+ 每 5 Batch 检查 CLAUDE.md 行数 |
| 批量文档 | 攒了 3 个 Batch 才补日志 → 遗漏决策 | 每 Batch 完成立刻写 requirements-log |
| 发现没登记 | 讨论中识别的 ⚠️ 问题没有写进 backlog | 发现即待办——当场修（≤2 文件）或登记 backlog（>2 文件） |

### 上下文反模式（会话管理阶段）

| 反模式 | 症状 | 纠正 |
|--------|------|------|
| 上下文膨胀 | 跨 3 话题 / 2+ Batch 不重启 → reasoning 退化 | 每次 commit 后主动评估 → 备份状态到文档 → 建议 `/clear` |
| 工具调用串行化 | 每步逐个调工具 → 22 turns 完成 2 文件 Batch | Blast 模式：同阶段内并行（信息采集 1 turn · 编辑 2-3 turns · 验证 1-2 turns · 闭合 2 turns） |
| 流程漏洞无人认领 | 发现低效模式 → 等用户指出才改 → 同类错误重复 3+ 次 | AI 也是流程 owner：相同错误 ≤2 次，主动提案落地到 CLAUDE.md/methodology.md |

### 代码阶段反模式（未来适用）

| 反模式 | 症状 | 纠正 |
|--------|------|------|
| 测试后补 | 「写完再补测试」→ 永远不补 | 先写测试，确认失败，再写实现 |
| 测试骨架退化 | 2-3 条 golden path 后无人追问边界 | `make check-docs` L2e 扫描：≤3 条测试 → 告警 |
| 凭猜测调 CSS | 改 `padding-top: +4px→+2px→+0px` 均不生效 | 先用 Playwright 拿到实际 px 值 → 遍历父链找注入源 → 再改 |
| 共享模块无风险评估 | 改 `api/schemas.py` 一个字段 → 14 个消费者炸了 3 个 | Plan 阶段做 Consumer Impact Analysis + Layer Enumeration |

> 反模式速查不是文档——是开工前 30 秒的防御性扫描。每次 Pre-flight 后扫一遍，确认自己不在任何已知陷阱中。

### 行为协议（行为层防呆 — P100-B57 落地）

## 流程改进：三层沉淀架构

```
复盘发现漏洞
    │
    ├─ 层次 1 · CLAUDE.md    — 规则描述层（"什么时候该做什么"）
    ├─ 层次 2 · methodology.md — 方法论提炼层（"为什么 + 怎么迁移"）
    └─ 层次 3 · 机械防呆     — 强制执行层（hook/lint/check 脚本）
```

每次复盘问三个问题：
1. 规则写进 CLAUDE.md 了吗？
2. 通用模式提炼到 methodology.md 了吗？
3. 有没有机械手段能兜底？

**LRN → 防呆转化的必经之路**（从 GlassCortex 移植）：

经验沉淀（LRN）写入 pitfalls/lessons-learned 只是层次 1+2。缺少层次 3 时，文字经验不会阻止复现。

**防呆转化 checklist**（每条 LRN 写入后强制执行）：
1. 这条 LRN 能转化为 lint rule 吗？→ 是则落地
2. 能转化为 `check-*` 门禁吗？→ 是则落地
3. 能转化为 pre-commit hook 吗？→ 是则落地
4. 能转化为 Plan checklist 项吗？→ 是则落地
5. 以上全否 → 标注 `机械门禁：暂不适用（理由）`，下次复盘重审

## 产品优先级四层框架（轻量版）

> 从 GlassCortex 移植。Synapse 作为平台项目，优先级判据待产品化后细化。
> 原则：**架构堵点优先（不做就大量返工），深度打磨延后。**

| 层级 | 名称 | 判据 | Synapse 举例 |
|------|------|------|-------------|
| **L0** | 架构堵点 | 不做会导致后续大量返工。每推迟一个 Batch，后面多花 N 倍成本 | 协议设计不一致 → 所有端点返工 |
| **L1** | 用户断点 | 用户走到这里会停下来、困惑、或不信任 | API 报错无结构化信息 |
| **L2** | 体验弧线 | 用户能走通，但感觉零散 | 端点命名不统一 |
| **L3** | 深度打磨 | 精致化、一致性。不影响走通 | 响应格式美化 |

**使用方式**：排期时从 L0 挑，再 L1→L2→L3。新需求入库先标层，再标 P0-P3。层级决定"什么时候做"，P 级决定"同层内谁先做"。

## 文档迁移策略（三阶段路线图）

> 来源：P7-003 文档迁移策略 · P100-B30 落地：`make db-sync` + 一致性门禁
### 背景

Synapse 的 Batch 状态同时存在于数据库（权威源）和 `docs/batch-status.md`（人类可读副本）。在阶段一（一式两份）期间，手工维护容易产生 DB 与文档的状态偏差——B43 抓出 12 处 doc↔code drift 就是双维护负担的直接症状。

### 三阶段路线

| 阶段 | 名称 | 描述 | 目标状态 |
|:---:|------|------|:---:|
| 一 | 一式两份 | DB + Markdown 并存，手工维护一致性 | ✅（2026-07-06 前） |
| 二 | 线上为主 | DB 为 primary source，`make db-sync` 从 DB 导出 docs | ▶️ P100-B30 落地 |
| 三 | 纯 DB 导出 | 外部需要时直接从 DB 导出，不维护手工 Markdown | ⬜ 远期 |

### 阶段二操作指南

**同步 DB → docs**：
```bash
make db-sync
```
从数据库读取 Synapse 项目的全部 Batch，按 order 排序，覆盖写入 `docs/batch-status.md`。不保留手工编辑内容。

**检查一致性**：
```bash
make check-db-consistency
```
比较数据库和 `docs/batch-status.md` 的 Batch 数量。已接入 `make check` 管道（警告级——不阻断 commit，对标 `check-doc-curl` 的首部署模式）。

**典型工作流**：
1. 在 Synapse Web UI 或 API 中更新 Batch 状态
2. 运行 `make db-sync` 刷新文档
3. 提交时 `make check` 自动验证一致性

### 设计原则

- **DB 是权威源**（single source of truth）——所有 Batch 状态变更在 DB 中发生
- **`docs/batch-status.md` 是只读投影**——不应手工编辑，由 `make db-sync` 生成
- **一致性门禁为警告级**——docs 滞后于 DB 是正常过渡态
- **升级为阻断的时机**——团队习惯"DB 为主"工作流后（估计 5-10 批），将 `check-db-consistency` 从警告升级为硬阻断
