# Synapse Phase 划分标准

> 来源：P7 方向讨论 + P100 治理 Phase 建立
> 最后更新：2026-08-07（P100-B116 文档全量刷新）

## Phase 的目的

**Phase 是"战略意图的容器"**——它回答的是「这一阶段我们要达成什么」，不是「我们有多少活要干」。

Phase 的存在理由：
1. **对齐** — 团队（人+AI）对"当前阶段在做什么"有一致理解
2. **边界** — 防止 scope creep，不属于这个 Phase 战略意图的工作推迟到下一 Phase
3. **节奏** — 每个 Phase 结束时的 L5 拉通是天然的质量 checkpoint
4. **追溯** — 事后回顾时，Phase 是比单个 commit 更有意义的时间单位

## 五维度判断标准

新建 Phase 时必须通过全部五项检查：

| 维度 | 判断逻辑 | 反例（不应建立 Phase） |
|---|---|---|
| **1. 主题一致性** | 所有 Batch 能用一句话概括 | "杂项收集" — 没有统一主题 |
| **2. 自然断点** | 结束时产品处于稳定可交付状态 | 中途切 Phase — 产品处于半成品状态 |
| **3. 规模阈值** | ≤100 Batch，如超需显式说明原因 | 1 Batch — 太小，应合并到相邻 Phase（除非是战略 Phase） |
| **4. 工作性质** | 工作性质与前后 Phase 有根本差异 | P6 做功能 → P7 也做功能，无性质变化 |
| **5. 战略意图** | 能用「完成 [X]，使 [Y] 成为可能」表述 | "把剩下的做了" — 没有清晰的终态 |

### 判断流程

```
提出 Phase 候选
  → 1. 一句话概括这个 Phase？（通不过 → 拒绝）
  → 2. 结束时产品状态？（不稳定 → 拒绝）
  → 3. 预计规模？（≤1 Batch → 合并到相邻 Phase；>100 Batch → 显式说明原因）
  → 4. 工作性质与前 Phase 不同？（相同 → 拒绝）
  → 5. 战略意图清晰吗？（模糊 → 拒绝）
  → ✅ 通过 → 写入 roadmap + master-backlog
```

## Phase 生命周期

```
提议 → 五维检查 → 排 Batch → 执行 → L5 拉通 → 关闭
```

- **提议**：用户或 AI 提出新 Phase 候选
- **五维检查**：AI 必须跑完上述 5 项并输出结论
- **排 Batch**：Phase 内 Batch 在 `docs/plans/` 中排批
- **执行**：每 Batch 走 Plan → 实现 → mypy → pytest → make check → commit
- **L5 拉通**：Phase 最后一批完成后强制 L5
- **关闭**：L5 通过后 Phase 标记完成

## 编号规范

### Phase 编号

| 范围 | 类型 | 说明 |
|------|------|------|
| P1-P99 | 功能 Phase | 产品功能开发，有明确的开始和结束 |
| P100-P199 | 治理 Phase | 工具链/门禁/方法论，持续开放 |
| P200+ | 保留 | 未来扩展 |

### Batch 编号

**Per-Phase 独立编号**：每个 Phase 的 Batch 从 B1 开始，不与全局连续。

- 格式：`P{Phase}-B{Batch}`（如 P8-B1、P100-B1）
- 全局编号（B1, B2, ... B56）为历史遗留，新 Phase 必须使用 Px-By 格式
- 同一 Phase 内 Batch 编号连续递增，不跳号

### 文档引用格式

- roadmap.md：`| Phase N Batch M |` 或 `| P{N}-B{M} |`
- requirements-log.md：`### P{N}-B{M}: 描述`
- CLAUDE.md 当前状态：`P{N}-B{M} 完成/进行中`

## 特殊 Phase 类型

### 治理 Phase（P100+）

**特征**：不关闭，持续接受新 Batch。用于工具链/门禁/方法论等持续演进的工作。

**建立条件**（比普通 Phase 更严格）：
- 工作性质明确为"治理/工具链"（不是功能开发）
- 有明确的准入标准（什么可以进治理 Phase，什么不行）
- 有定期修剪机制（避免无限膨胀）

**准入标准（≥2/4）**：
| 标准 | 说明 |
|---|---|
| □ 非功能开发 | 不新增产品特性，不改变用户可见行为 |
| □ 跨 Phase 复用 | ≥2 个功能 Phase 会受益 |
| □ 防呆/自动化 | 减少人工出错可能，或自动化重复操作 |
| □ 技术债清理 | 修复已知的设计偏差或代码质量问题 |

### 战略 Phase

**特征**：产出是决策和路线图，不一定是代码。Batch 可以是讨论、文档、原型验证。

**建立条件**：
- 战略方向需要重新评估或制定
- 当前 Phase 无法自然延续到下一 Phase
- 需要"停下来想一想"

## 常见错误

| 错误 | 说明 |
|---|---|
| 把 Phase 当文件夹用 | "P6 做完了，剩下的叫 P7" — 没有战略意图 |
| Phase 超大且无说明 | 100+ Batch 且未在 Phase 提案中提供明确理由 → 应解释为什么需要超大 Phase 或考虑拆分 |
| Phase 太小 | 1 Batch 的非战略 Phase → 应合并 |
| 工作性质无变化 | P5→P6→P7 如果都是"产品功能开发"，说明划分标准失效 |
| 跳过五维检查 | 惯性建 Phase，没有验证 |
