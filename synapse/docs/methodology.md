# Synapse 开发工作流方法论

> 从 GlassCortex 方法论移植 + Synapse 定制。
> 适配人机混合团队协调平台的开发。
> 版本：v2.0 · 2026-08-10（P14-B4 狗粮闭环 · L5 拉通 · 日期同步）
> 子文档：[`methodology-reference.md`](methodology-reference.md) — 五层自检金字塔 · SMG · 反模式速查 · 流程改进 · 优先级框架 · 规则映射 · 移植指南 · 迁移策略

## 八步链路

```
Pre-flight → Plan → 拆分 → 设计+验证交替 → 五层自检 → 文档闭环 → 推送 → 清理 Plan
```

每步跳过的代价随步数指数增长——第一步跳过的债，最后一步 10x 偿还。

（当前无代码阶段，"TDD"替换为"设计+验证交替"——先写场景推演定义预期行为，再做设计。代码阶段后切换为标准 TDD。）

## 0. Pre-flight — 开工前确认战场基线

**做什么**：每个 Batch 开工前，第一件事跑 `./tools/check-docs.sh`。确认四件事——L1-L4 上一批是否有记录、L5 拉通自检累积几批了、有没有文档落后于需求日志、日报是否缺失。

**为什么**：开工前不知道 L5 已累积 5 批，做到一半才发现要补救——返工成本是开工前知道的 10 倍。门禁挡在开工前，不挡在交付后。仅输出警告而不退出非零 = 不是门禁，是噪音。

**Synapse 落地方式**：
- 每个 Batch 第一条工具调用：`./tools/check-docs.sh`
- L5 累积 >2 批 → 工具 `exit 1`（硬失败），不能仅输出警告
- 文档过期 → 先刷新文档，再开工
- L1-L4 记录完整性：grep requirements-log 最新 Batch 条目是否包含 L1-L4 breakdown
- 这不是"检查是否通过"，是"确认战场状态"——知道哪里有问题比通过更重要

**依赖升级纪律**（代码阶段后适用）：每次 `npm install` / `pip install` 后跑全栈门禁。当前 Synapse 无代码依赖，此条暂不激活。

## 1. Plan — 先设计，再动手

**做什么**：用 AI 的 plan mode 输出设计文档。包含：要改哪些文件（文档/模型/协议）、备选方案及放弃理由、影响范围评估。

**为什么**：没有 Plan 的改动 = 边开飞机边画图纸。返工成本最高——改到一半发现设计前提是错的，前面全白做。

**跳过代价**：改 3 个文件时发现第 1 个文件的设计假设被第 2 个推翻 → 全部重写。

**Synapse 落地方式**：
- 按 [Plan 分级](#plan-分级--按-batch-规模选择-plan-模式) 匹配模式——🟢 微型（≤2 文件+无接口变更）inline Plan · 🟡 标准（3-4 文件）精简 Plan · 🔴 大型（≥5 文件）完整 Plan
- Plan 三问：改哪些文件、备选方案、影响谁
- Plan 阶段逐文件列出变更清单+计数，≤8 放行，>12 必须拆（详见 §2 机械门禁）

**Shared Module Risk Assessment**（代码阶段后完整适用）：当 Plan 涉及 ≥3 消费者引用的模块时，须做 Consumer Impact Analysis + Layer Enumeration。当前 Synapse 消费者 <3，此条作为参考框架保留（详见 §Shared Module Governance）。

### Plan 分级 — 按 Batch 规模选择 Plan 模式

> 从 GlassCortex 审计移植（2026-07-06）。并非所有 Batch 都需要完整的 EnterPlanMode 流程。按文件数和接口影响分级，减少微型 Batch 的 Plan 往返开销。

| 级别 | 条件 | Plan 方式 | 预期轮数 |
|:---:|------|---------|:-------:|
| 🟢 微型 | ≤2 文件 + 无接口变更 + 无新增共享模块 | inline 口头 Plan，1 轮确认，**不 EnterPlanMode** | 1 |
| 🟡 标准 | 3-4 文件 或 接口签名变更 或 新增 ≥3 消费者的模块 | EnterPlanMode → 精简 Plan（改哪些文件 + 影响谁） | 2 |
| 🔴 大型 | ≥5 文件 或 架构变更 或 共享模块重构 | EnterPlanMode → 完整 Plan + Consumer Impact Analysis + Risk Assessment | 3 |

**判断流程**：
1. **先数文件**：Plan 阶段预估变更文件数（与 §2 文件计数门禁共用）
2. **再判断接口影响**：有没有改 API schema / 数据模型字段 / 协议定义 / 组件 props？
3. **匹配级别** → 执行对应 Plan 模式

**与文件数门禁的关系**：分级管「Plan 怎么画」，门禁管「Batch 拆多大」。两套正交互补：

| 场景 | Plan 分级 | 文件门禁 |
|------|:---:|:---:|
| 修一个 typo（1 文件，无接口变更） | 🟢 微型（inline Plan） | ≤8 ✅ 放行 |
| 新增一个 API 端点（3 文件，接口变更） | 🟡 标准（精简 Plan） | ≤8 ✅ 放行 |
| 重构数据模型（6 文件，架构变更） | 🔴 大型（完整 Plan） | ≤8 ✅ 放行，但接近上限 |
| 全栈跨层变更（12 文件，架构变更） | 🔴 大型（完整 Plan） | 9-12 ⚠️ 需豁免或拆分 |

**为什么分级**：微型 Batch（修 typo、改常量、加一行日志）的 EnterPlanMode 往返（写 Plan → 用户审批 → 退出）可能比编码本身更长。Plan 的核心价值是「想清楚再动手」——当变更足够简单以至于没有歧义时，Plan 的形式应该简化，但核心理念（先想清楚）不省。

**反模式警示**：
- 「小改动豁免幻觉」：三行代码被脑内归为 trivial fix → 跳过 Plan/roadmap 登记/五层自检。**零例外原则**：1 行和 100 行走同一套启动流程（建 Batch → 跑门禁 → 登记 roadmap → 动手）。Plan 形式可简化（🟢 inline），但流程步骤不跳。
- 「分级降级」：本该是 🔴 大型的变更因为「不想写完整 Plan」而降级为 🟡。判断标准是客观条件（文件数 + 接口影响），不是主观感受。

**Scout→Execute 分级重评**（详见 CLAUDE.md §13）：Plan 分级不是一次性判断。Scout 阶段可能发现变更范围远超预估 → 必须 stop + 重走 Plan 流程（重新分级、重新 EnterPlanMode），不得将 Scout 发现的新增变更直接并入执行。触发信号：文件数超阈值 / 新增登记项 ≥3 / 新文件类别 / 接口变更。

## 2. 拆分 — 批次粒度 ≤4 个任务

**做什么**：把 Plan 拆成 2-4 个任务的批次。每个任务可独立验证、可独立交付。模糊需求在拆分阶段暴露，不在执行阶段暴露。

**为什么**：人脑一次只能 hold 住 2-4 个任务。超过 4 个任务的批次，中间步骤依赖必然出错。

**跳过代价**：一把全做 → 中间步骤隐含依赖没发现 → 写到第 5 个文件时发现第 2 个文件给的接口不对 → 返工重量级。

**Synapse 落地方式**：
- 问自己："这批完成后的验证方式是什么？"答不上来 = 拆分不够细
- 每批 ≤4 个任务，验证不过不进下一批
- 模糊点先澄清再动手，不靠假设推进

### Batch 文件数机械门禁

> 新增于 2026-07-04，P4-B9 复盘。防堵 "计划 8 实际 15" 的颗粒度假象。

**Plan 阶段强制执行**：

1. 在 plan 文件末尾追加「文件计数」段，逐文件列出
2. **拆分决策**：

| 文件数 | 决策 |
|:--:|------|
| ≤8 | 单 Batch，放行 |
| 9-12 | 全部机械变更（≤3 行/文件，同一类型）→ 可申请豁免，须在 plan 中显式注明。否则必须拆 |
| >12 | 必须拆，不讨论 |

3. **锁定**：用户批准 plan 后文件清单即锁定。实现中发现新文件需改 → 新 Batch。

详见 memory: [[batch-size-precommit-gate]]

## 3. 设计+验证交替

> 当前无代码阶段，TDD 的"测试"替换为"场景推演"。代码阶段后切换为标准 TDD。

**做什么**：先写场景推演定义预期行为，再做设计。每完成一个文件/模块立刻验证（结构检查、引用交叉验证），通过再开下一个。

**为什么**：逐文件验证把问题爆炸半径限制在单文件。攒到最后一起跑 → 多个文件的错误互相遮蔽。

**当前阶段（设计）**：
- 写场景推演 → 确认推演暴露了设计问题 → 修改设计 → 推演通过 → 下一个模块
- 验证手段：L1 结构完整性 + L2 引用可解析 + L3 契约三方对齐

**代码阶段后**：
- 先写测试 → 跑一下确认失败（证明测试有效）→ 写实现 → 跑绿 → 下一个文件
- 质量门禁配 pre-commit hook，自动拦截不合规提交
- 不加预判性 `# type: ignore`，先跑了再说

## 5. 文档闭环 — 需求→执行→验证→日志

**做什么**：每完成一个 Batch，立刻同步更新：架构文档、需求日志（做了什么、为什么、验证方式）、踩坑记录（如果有）。不等攒到收尾批量补。

**为什么**：48 小时内遗忘 70% 的决策上下文。收尾批量补 = 靠回忆写文档 = 遗漏关键决策。

**跳过代价**：3 周后回来问"这个设计为什么是这样的"→ 日志是空的 → 只能重读全部文档反向推演。

**Synapse 落地方式**：
- 需求日志模板：`日期 | 做了什么 | 为什么 | 验证方式(手动/自动/暂不验证)`
- 每 Batch 完成立刻写，不是"等下补"
- 规范变更触发方法论审查：改 CLAUDE.md → 立即检查 methodology.md 是否需要同步

### 日报铁律

**做什么**：每个工作日结束时，在 `docs/daily/YYYY-MM-DD.md` 记录当天完成的工作、关键决策和遗留问题。日报是文档闭环的日常载体——不是"有时间才写"，而是"忘了就补"的制度约束。

**为什么**：
- **分布式团队的异步同步通道**：人+Agent 混合团队中，成员可能在任意时间工作。日报是唯一的异步状态同步机制——下一个接手的 Worker（人或 Agent）读到日报就能接上上下文，不需要从 git log 反向推演
- **降低上下文重建成本**：新会话读到日报 → 3 分钟了解昨天做了什么。没日报 → 只能从 commit message + diff 反推 → 20 分钟起步，且遗漏关键决策理由
- **48 小时遗忘曲线**：48 小时内遗忘 ~70% 的决策上下文。当天 5 分钟写日报 vs 两天后 30 分钟靠回忆补——前者是投资，后者是负债

**跳过代价**：
- **工作进展断裂**：跨天/跨批次的工作缺少衔接点 → 新会话不知道"上次做到哪了" → 要么重复做、要么漏做
- **"做了什么"可反推，"为什么"不可还原**：git log 能告诉你改了哪个文件，不能告诉你为什么选方案 A 不选方案 B。日报缺失 = 决策理由永久蒸发
- **项目健康度不可审计**：管理层（人或 P9/P10 Agent）无法从日报判断项目是否在轨道上 → 等到 roadmap 偏离才发现 → 返工成本 10x 起步

**落地规则**：
- **同日追加**：同一天的工作总是追加到同一个日报文件，不新建
- **跨天新建**：日期变更后创建新文件 `docs/daily/YYYY-MM-DD.md`
- **机械门禁**：`./tools/check-docs.sh` 自动检查昨天日报是否存在，缺失则告警
- **门禁不拦 commit**：日报允许补写（从 git log 反推），只告警不阻断——但补写的日报只能还原"做了什么"，还原不了"为什么"
- **忘了就补**：从 `git log --since="YYYY-MM-DD"` 反推，补写的日报注明「补」

### 编号体系

- **Phase 1-99**：产品 Phase，Batch 在 Phase 内从 1 递增
- **P1-P5**：MVP Sprint（当前），按优先级分组
- **Batch 编号原子性**：commit 前检查上一 commit 编号连续递增，不连续 → pre-commit hook `exit 1`
- **格式统一**：commit message 禁止简写 `BN`，必须写全 `Phase N Batch M`

### 跨轨道 ID 迁移协议（S→G / 通用）

> **背景**：P9-B89 Scout 将 S-042（空 catch 修复）和 S-043（分页契约）排入 P9-B94/B95。执行中发现这两项本质是代码治理而非产品功能。纠正后 S-042→G21、S-043→G22，这是 Synapse 首次跨轨道重分类。协议从此案例提取，适用所有轨道间迁移。

#### 触发条件

当 master-backlog 中已登记的 S-xxx 项满足以下条件时，启动跨轨道迁移：

1. **性质误判**：该项本质属于另一轨道（如代码卫生项被登记为产品功能 S-xxx，应归 P100 治理 G-xx）
2. **轨道变更**：战略决策将某项从当前轨道移至其他轨道（如 P9 产品 → P100 治理）

#### 迁移步骤

| 步骤 | 操作 | 位置 |
|:--:|------|------|
| ① | 在目标 backlog 中按该轨道编号体系分配新 ID（如 P100 治理 → G-xx） | tracks/synapse.md P100 backlog 表 |
| ② | 新 ID 条目必须标注原始来源（D-P9-xxx）和原 ID，确保双向可追溯 | 同上 |
| ③ | 在 master-backlog 中将原条目状态改为 `⤵ <新ID>`（非 ⬜/✅），保留历史引用 | docs/master-backlog.md |
| ④ | 如涉及批号作废（原计划在旧轨道执行的 Batch 编号），在 track 跳号登记表中标注 | tracks/synapse.md 跳号登记表 |
| ⑤ | 更新目标轨道的 backlog 计数（如 P100 20→22 项） | tracks/synapse.md 指针表 |

#### 编号空间隔离

| 前缀 | 轨道 | 含义 | 示例 |
|:---:|------|------|------|
| `S-` | master-backlog P2 段 | 产品功能/故事项 | S-037, S-044 |
| `G-` | P100 治理 backlog | 代码质量/工具链/流程治理项 | G1, G21 |
| `M-` | master-backlog P0 段 | 阻塞性必需项（Makefile/门禁） | M-001 |
| `F-` | master-backlog 远期段 | 远期不适用项 | F-001 |
| `D-Px-` | Session memory 🧭 段 | 战略讨论编号（来源追溯） | D-P9-012 |

> **关键约束**：同一工作项不得在两个编号空间同时作为活跃项存在。迁移后原 ID 变为 `⤵` 跳转指针，只有目标 ID 是活跃工作项。

#### 追溯链格式

```
D-P9-012（原始讨论）
  └─ S-042（master-backlog 原 ID）→ ⤵ G21（迁移状态）
       └─ G21（P100 backlog 活跃工作项）
```

## 5.5 Fresh-eyes 复审 — L3 契约层验证的最后一道防线

**做什么**：契约变更批（改 API/schema/protocol/onboarding/config）close 前必须过 **fresh-eyes 复审**——新会话隔离，同一 checklist 逐条对源码 grep，专门抓漏。

**为什么**（LL14 精要）：同批自审 = 必要不充分。执行者视线焦点在"我改了什么"，端点表/字段被反复扫过但心理跳读；时限压力下"赶紧收尾 commit" 压过 "再核一遍" 的耐心；同会话工具链共享让门禁绿灯变成"我这波合格"的心理暗示。fresh-eyes 是**流程原子性的机械保证**——把"自审"和"复审"物理隔离到不同会话/上下文，避免心理污染。

**触发场景**（任一即需 fresh-eyes）：
- `docs/onboarding.md` 或用户 API 表变更
- `src/api/*.py` / `src/schemas/*.py` / `docs/protocol.md` 变更
- `docs/data-model.md` 或数据模型 migration
- Config/env 契约变更（新增/删除关键配置）

**机械化路径**（G-007 · P100-B25 落地）：

| 层 | 手段 | 触发点 |
|:--:|------|-------|
| **软** | 契约变更批 checkpoint 强制含 §Fresh Eyes Review Checklist | 人力自觉 · 会话末段 |
| **硬** | `tools/post-commit.sh` 检测 commit msg 关键词（onboarding/protocol/schema/api/contract/契约）→ 写 `.git/synapse-pending-fresh-eyes` marker | post-commit 时机自动 |
| **补** | `tools/check-fresh-eyes.sh` pre-commit gate 读 marker · 未清除 → 警告 · 验证期后升级阻断 | make check · 下批 commit 前 |
| **闭环** | commit msg 含 "fresh-eyes" 关键词 → post-commit 自动清 marker | 自证机制 |

**Fresh-eyes checklist 骨架**（模板）：
- 按功能维度逐条列出 doc 声明的行为（"文档说 X 端点接受 Y 字段，返回 Z 结构"）
- 对每条：`grep` 源码找实现点 → 对照字段/类型/位置/权限 → 打勾/打叉
- 不看已 commit 的 doc/diff，只看 doc 现状 + 源码现状
- 抓漏后：先记录漏检项到 pitfalls · 再修 doc/code · 最后 commit msg 含 "fresh-eyes"

**与五层自检金字塔的关系**：
- L1 结构 / L2 引用 / L4 场景 → 同批可完成
- **L3 契约 → 必须跨会话 fresh-eyes 才 close**
- L5 拉通 → 每 2 批一次（含 fresh-eyes 结果的叙事一致性检查）

**判断准则**：**契约层变更 close 前必须过 fresh-eyes。** 同批自审证明"我按 plan 做了"，fresh-eyes 证明"结果对齐真相"——两者都做，L3 才真正闭环。参考 `docs/lessons-learned.md` LL14 完整推理。

## 5.6 文档生命周期 — 创建/成长/归档/删除

**做什么**：文档不是只增不减的 append-only 日志。每份文档都有生命周期：创建时有准入标准，增长时有大小阈值，过期时有归档路径，冗余时有合并/删除机制。

**为什么**（G25）：requirements-log.md 7959 行占全量文档 31%，CLAUDE.md 440 行超阈值，每批 doc overhead 6-7 files。无生命周期 = 文档熵增不可逆 → 新人阅读成本递增 → 文档可信度递减（越臃肿越没人看 → 越没人看越不维护 → 恶性循环）。

### 创建标准

新文档必须满足至少一条：

| 条件 | 示例 |
|------|------|
| ≥200 行独立主题，拆分后父文档仍 ≥100 行 | 从 architecture.md 拆出 security-model.md |
| 新架构子系统，有独立读者群 | worker-admin-interaction-flow.md |
| 新角色 Skill 模板 | `docs/templates/role-*.md` |
| 工具脚本有 ≥3 个消费者 | `tools/check-*.sh` 对应的 methodology 段 |

不满足 → 追加到已有文档而非新建。

### 大小阈值

| 阈值 | 级别 | 动作 |
|:---:|:---:|------|
| >400 行 | ⚠️ WARNING | 评估是否可拆分/归档 |
| >800 行 | ⚠️ WARNING（当前）→ 🚫 ERROR（P100-B73 升级） | 需拆分或归档。当前为警告级（首部署过渡期），后续升级为硬阻断 |
| requirements-log >10000 行 | ⚠️ WARNING | 历史条目归档到 `docs/archive/` |

**机械门禁**：`tools/check-docs.sh` 文件健康诊断段。

### 归档规则

| 触发条件 | 归档路径 |
|---------|---------|
| Phase 完成且该 Phase 全部 Batch 已闭环 ≥7 天 | 历史批次入口段 → `docs/archive/` |
| 文档 >90 天无更新且无未闭环待办引用 | 标记 `⚠️ archive-candidate`，下个 Phase 结束前归档 |
| 被替代的旧版文档（如 v1 协议被 v2 全面替换） | 移入 `docs/archive/`，在原位置留 redirect 指针 |

### 合并规则

| 触发条件 | 动作 |
|---------|------|
| 两文档主题重叠 >50%（如两篇都讲授权但分在不同文件） | 合并到覆盖面更广的那篇 |
| 文件 <50 行且无独立导航价值（纯指针/纯引用） | 合并到父文档，原位置留一行 `→ 见 [父文档](parent.md) §N` |

### 删除标准

| 条件 | 动作 |
|------|------|
| 信息已在代码中可验证（如 curl 示例被 API docstring 充分覆盖） | 删除 curl 块，留概念说明 |
| Plan 文件已执行完毕 >30 天 | 删除（执行结果已在 requirements-log + git log 中） |
| 内容已完全过时且无历史参考价值 | 删除，commit msg 注明删除原因 |

### 三层引用对齐合约

CLAUDE.md §当前状态、tracks/synapse.md、master-backlog 三处对同一议题的描述必须一致。这是 G26 定义的机械合约：

| 检查项 | 频率 | 工具 |
|--------|:---:|------|
| 议题编号连续无跳号 | 每批 | `tools/check-issue-numbers.sh` |
| 议题状态（✅/🔄/⬜）三方一致 | 每批 | 同上 |
| track 段头 Batch 范围 = 实际最后一批 | 每批 | 同上 |
| CLAUDE.md 当前状态段议题数 = track 定义议题数 | 每批 | 同上 |

**不一致 → WARNING（不阻断 commit）**，但连续 2 批未修复 → 升级为 ERROR 阻断。

## 6. 推送 — 原子提交，遵守规范

**做什么**：`git commit` 的 message 写清楚"做了什么、为什么"，不是"修改了哪些文件"。commit 前缀用项目名（`synapse:`）。

**为什么**：commit message 是 3 个月后唯一能快速理解一段变更的入口。`git log` 读到的应该是决策记录，不是文件清单。

**落地方式**：
- 提交格式：`synapse: 一句话描述 — 关键细节`
- 绝不用 `--no-verify`、`--no-gpg-sign` 等跳过 hook 的 flag
- pre-commit hook 自动跑文档检查，不过不提交

---

## 7. 清理 Plan — 脚手架下架

**做什么**：推送完成后，删除 Plan 文件（`~/.claude/plans/` 或 `docs/plans/`）。Plan 是施工期间的临时脚手架，代码/文档是永久资产。

**为什么**：残留 Plan 文件 = 下次启动新 Plan 时要先判断"哪个是当前的、哪个是历史的"——心智负担比文件本身价值大。

**落地方式**：
- 推送后立刻 `rm` 对应 Plan 文件
- Git history 保留了设计意图，删文件不丢信息

## 上下文管理：预防 Reasoning 退化

AI agent 的推理质量随上下文膨胀而衰减——这是已知的系统性限制，不是偶然失误。预防策略：

1. **任务前预估**：多轮探索/规划/决策后、跨话题 >3、或 2+ Batch 未重启 → 上下文已膨胀
2. **备份到项目文档**：Plan + 未完成任务 + 关键决策 → 写入 roadmap 或 requirements-log
3. **主动建议重启**：告诉用户"重启后从 X 文档 Y 段接续"，不等到用户发现质量下降
4. **接头暗号**：每次 `/clear` 前约定一个简短的接头暗号（如「启动 P5-B2」）。新会话首条消息说出暗号 → AI 直接从 memory 定位上下文

**为什么**：上下文退化 + reasoning 退化是双螺旋下坠。重启成本 2 分钟远低于纠错成本。

## 核心理念

不是"流程越重越安全"，而是"约束落在最容易忘的地方"：

- Plan 和拆分 → 约束"想清楚再动手"
- 设计+验证交替 → 约束"问题爆炸半径"
- 五层自检 → 约束"语法过不等于交付完"
- 文档闭环 → 约束"人类记忆衰减曲线"
- Plan 清理 → 约束"脚手架比房顶先烂"

每个约束都是在对抗一种自然倾向：想省时间跳过设计→返工、想多写几个文件一起验→返工、想攒到最后一起补文档→遗忘。

> 这套方法论并非不可变通。但每次想跳过一步时，先问自己：省下的时间，够不够付返工成本？
